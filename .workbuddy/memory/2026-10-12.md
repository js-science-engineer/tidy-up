## 环境坑：GitHub 网页通道被阻断时的推送办法（可复用）
- 现象：`github.com:443` 完全连不上（DNS 正常解析到 20.205.243.166，换 140.82.x/20.27.x 各 IP 均超时），但 **`api.github.com` 正常**；`ssh.github.com:443` 也不可达；本机无任何可用代理端口（6227/7890/10809/1080… 全无响应）。→ `git push` 无法工作。
- **解法：走 GitHub REST API 手动生成 tree/commit 并推进 ref**，等价于 push：
  1. bash 侧导出：`git rev-parse HEAD` / `HEAD~1`、`git log -1 --pretty=%B|%an|%ae|%aI`、`git diff --name-only`，逐个 `git cat-file blob "HEAD:$f" | base64 -w0` 与 `git rev-parse "HEAD:$f"`（**必须取 git 对象库内容**，不要直接读工作区文件，避免 CRLF 差异）。
  2. Node 侧：token 取自 `~/.git-credentials`（形如 `https://user:token@github.com`）→ `POST /git/blobs`（encoding base64）→ `POST /git/trees`（base_tree + 仅变更项）→ `POST /git/commits`（含 author/committer 与 date）→ `PATCH /git/refs/heads/main`。每个 blob 的返回 sha 与本地 `rev-parse HEAD:path` 对比可自证内容一致。
  3. **注意**：Node 里 `execFileSync('git', …)` 报 `EBUSY`（沙箱/进程限制），所以 git 命令一律在 bash 侧执行，Node 只做 HTTP。
- **让本地与远端 sha 完全对齐**（避免假「分叉」）：GitHub 会把提交 message 多补一个尾换行（本次实测为 `message + "\n\n"`，时区沿用 `+0800`）。用 Node crypto 直接算 `sha1("commit <len>\0" + content)` 遍历少量参数组合即可复现同一响应 sha，命中后用 `git hash-object -t commit -w --literally --stdin < raw` 写入对象，再 `git update-ref refs/heads/main <sha>` + `refs/remotes/origin/main <sha>`，`git status` 即恢复干净。
