# 2026-10-16 工作记录

## 需求咨询：实验室成员共享同一份收纳数据（用户提出）
用户诉求：线上站现在「一人一账号」，但实验室是公共区域，希望同一实验室的人能共同查看（可能还有共同编辑）同一份收纳空间与物品。问能否用「密钥链接或其他方式」实现。

### 现状核查（实查线上云环境，applicationId=wbapp_1XLN5W4o7DF39CpWBV6u7D）
- 云数据库 10 张业务表全部 `RLSOn=true`：zones/cabinets/shelves/boxes/items/item_images/placements/logs/intake_queue 的策略**一律是 `owner_id = auth.uid()`**（sel/ins/upd/del 四件套）；仅 `categories` 为公开读（`USING true`）。
- 因此跨账号完全互不可见，是设计如此，不是 bug。
- 云存储路径规则（官方文档 `storage/management.md`）：`user_private` = `users/<uid>/...`（仅本人+管理员可读）；`app_shared` = `shared/<uid>/...`（**已登录的应用用户**均可读，仅 owner 可改删）。
- 终端用户：已注册 **2 个**邮箱账号（2026-10-05 创建）。UID 字段该接口未返回。
- `storage_list_owners` 工具调用报错：`DATABASE_42883 operator does not exist: bigint ~~ text`（工具侧 SQL bug，非本项目问题）。
- 云服务官方支持的 RLS 写法包含 **Team-shared**：`USING (team_id IN (SELECT team_id FROM team_members WHERE owner_id = auth.uid()))` —— 说明「实验室共享」是官方支持的权限模型。

### 给出的三条候选路径（已向用户呈现，等待选择）
1. **公用账号**（零开发）：全实验室共用一个邮箱账号密码。缺点：无操作人归属、验证码登录会互踢、改密码需通知全员。
2. **免登录密钥链接（只读）**：`SECURITY DEFINER` RPC + token 校验返回快照。**硬限制：图片取不到**——存储只对已登录用户开放，匿名访客无法签发 URL；只能把缩略图压缩成 base64 内嵌进快照（体积/时效风险），且不能编辑。
3. **实验室共享空间（推荐）**：新增 `labs` + `lab_members`，业务表加可空 `lab_id`，RLS 改为「本人 or 本实验室成员」；图片改存 `shared/<uid>/labs/<labId>/`；邀请链接 `?join=CODE` 或 6 位邀请码加入；前端加空间切换器与成员列表；现有数据可一键升级为实验室空间。
   - 风险点：`shared/` 前缀的读权限是「应用内所有已登录用户」，实验室级隔离靠「路径不可猜 + 数据表 RLS」，不是存储层按 lab 鉴权。
   - 实现要点：RLS 里避免逐行子查询，建议用 STABLE 函数返回 `my_lab_ids()`；`lab_members` 自身策略须为 `user_id = auth.uid()` 以避免递归。

### 用户决策（本日采纳）
- 共享方案：**实验室共享空间**（方案 3）。每个成员保留自己账号，共用一套柜子与物品，可出入库，操作可追溯到人。
- 数据迁移：**把现有账号数据升级为实验室空间**（`lab_id IS NULL` 的行一键改为该 lab）。

### 事故：重新发布丢掉了 TIDY_CLOUD=1，线上静默退回本地模式
**现象**：用户打开线上站发现顶栏没有「空间胶囊」，侧边栏也没有「实验室」。
**根因**：云端模式的唯一开关是环境变量 `TIDY_CLOUD=1`（`server/index.js` 的 `/api/system/info` 读它）。
2026-10-05 首次部署时该变量带上了；本次重新发布显式传了 `language: "node"`，启动命令被重新探测成默认
`npm start`，变量丢失 → 服务端报 `cloud:false` → `boot.js` 把 `store.mode` 置为 `local` →
没有登录页、`TopBar` 的 `v-if="isCloud"` 空间胶囊不渲染、SideNav 过滤掉 `cloudOnly` 的「🧪 实验室」。
**修复（两次尝试，第一次不够）**：
1. `server/index.js` 增加同域兜底判定 —— 云模式 = 存在 `server/cloud-config.json`
   且（`TIDY_CLOUD === '1'` 或 请求域名与配置的 `endpoint` 主机名完全相等）。
   取 `x-forwarded-host` 优先、回退 `host`，去端口、转小写；严格相等避免 `xxx.host.evil.com` 后缀冒充。
   **实测无效**：发布后线上 `cloud` 仍是 `false`——反向代理并没把公网域名放进 `Host`/`X-Forwarded-Host`，
   转发过来的是内网地址（`172.24.0.28:5175`）。所以不能靠域名判断。该兜底逻辑保留（无害，多一层保险）。
2. **真正的修复**：新增 `server/start-cloud.js`（内部 `process.env.TIDY_CLOUD = '1'` 后 require `./index.js`），
   `package.json` 增加脚本 `"start:cloud": "node server/start-cloud.js"`。
   发布时传 `startCmd: "npm run start:cloud"`。把开关写进代码而不依赖 shell 的 `VAR=1 cmd` 前缀写法，
   跨平台一致、也不怕启动命令被重新探测。本地 `npm start` 仍是不带开关的本地模式，行为不变。
   **发布后验证通过**：`cloud` 返回云配置对象（endpoint + publishableKey）。
**回归测试**：`test/m7.cloud.test.js` 新增 `M7.14`（自定义 Host / X-Forwarded-Host：同域命中、
带端口命中、本机不命中、后缀冒充不命中）与 `M7.15`（spawn `server/start-cloud.js` 且显式删掉
`TIDY_CLOUD`，仍须返回云配置）。全量 `npm test` = **89/89 通过**。
