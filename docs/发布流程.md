# 发布流程

本仓库有**两套产品共用一个仓库**，发布时用 **tag 前缀**区分。自动化流程见 [`.github/workflows/release.yml`](../.github/workflows/release.yml)。

| 产品 | 发布 tag | 产物 | 由谁构建 |
|---|---|---|---|
| 网页版 TidyLab | `web-v0.7.0` | 源码快照（GitHub 自动附带）+ Release 正文 | 纯发布，无需构建；线上部署是独立步骤 |
| 桌面版 js-pet | `desktop-v0.1.0` | `js-pet-0.1.0-setup.exe` + `js-pet-0.1.0-portable.exe` | GitHub Actions（windows-latest） |
| 桌面版 · macOS | 手动触发工作流 | `js-pet-0.1.0-arm64.dmg` / `-x64.dmg` | GitHub Actions（macos-latest，未签名） |

> ⚠️ **安装包不进仓库**（每个约 90~110 MB，`.gitignore` 已排除），
> 因此 **GitHub Releases 是用户获取安装包的唯一途径** —— 发布这一步不能省。

## 一、发布前：改版本号

### 网页版

| 位置 | 改什么 |
|---|---|
| `package.json` | `"version": "0.7.0"` |
| `server/index.js` | `GET /api/system/info` 返回里的 `version: '0.7.0'` |
| `CHANGELOG.md` | 新增该版本条目 |
| `docs/发布说明_v<版本>.md` | 新增发布说明（Release 正文会取这个文件） |

### 桌面版 js-pet

| 位置 | 改什么 |
|---|---|
| `desktop/package.json` | `"version": "0.1.0"` —— **安装包文件名取自这里** |
| `desktop/docs/release.md` | 更新发布说明 |
| `CHANGELOG.md` | 新增该版本条目 |

改完提交并推送到默认分支：

```bash
git add -A
git commit -m "chore: 版本号升至 0.7.1"
git push origin main
```

## 二、发布桌面版（最常用）

```bash
# 1) 在默认分支上打 tag 并推送
git tag desktop-v0.1.0
git push origin desktop-v0.1.0
```

推送 tag 后，GitHub Actions 自动执行：

1. **测试**：网页版 66 项 + 桌面版 113 项，任一失败即中止发布；
2. **构建**：在 `windows-latest` 上 `npm ci && npm run build:win`，产出 NSIS 安装版与便携版；
3. **发布**：创建同名 Release，把 `desktop/dist/*.exe` 作为附件上传。

几十秒后到 **Releases** 页面即可看到产物。

> 想改 tag 重新发：`git tag -d desktop-v0.1.0 && git push origin :refs/tags/desktop-v0.1.0`，再重新打。

---

## 三、发布网页版

```bash
git tag web-v0.7.0
git push origin web-v0.7.0
```

Actions 会创建 Release：
- 正文优先取 `docs/发布说明_v0.7.0.md`（存在时）；
- 否则用 GitHub 自动生成的变更说明（分类规则见 [`.github/release.yml`](../.github/release.yml)）；
- 源码 zip / tar.gz 由 GitHub 自动附带。

> **线上部署是独立步骤**，不由本工作流完成。部署后请实测一次「注册 → 录入结构 → 传图识别入库 → 搜索命中」的完整闭环。

## 四、构建 macOS 安装包（手动）

Windows 环境无法构建 mac 包，工作流提供手动入口：

1. 打开仓库 **Actions → Release → Run workflow**；
2. 勾选 **「构建 macOS dmg（未签名）」** → Run；
3. 构建完成后在该次运行的 **Artifacts** 里下载 `js-pet-macos-dmg`；
4. 手动把 dmg 上传到对应 Release（`gh release upload desktop-v0.1.0 js-pet-0.1.0-arm64.dmg`）。

**未签名说明**：未经 Apple 签名/公证，首次打开会被 Gatekeeper 拦截，用户需**右键 → 打开**放行一次。相关说明见 [`desktop/docs/install-macos.md`](../desktop/docs/install-macos.md) 与 [`desktop/docs/BUILD_MAC.md`](../desktop/docs/BUILD_MAC.md)。

## 五、无 CI 时：本地手动构建

```bash
cd desktop
npm install
npm test
npm run build:win     # Windows 上构建，产物在 desktop/dist/
npm run build:mac     # 需在 macOS 上执行
```

国内网络下载 Electron 超时时先设镜像：

```bash
set ELECTRON_MIRROR=https://npmmirror.com/mirrors/electron/   # Windows CMD
export ELECTRON_MIRROR=https://npmmirror.com/mirrors/electron/ # macOS / Linux
```

构建完成后，到 GitHub **Releases → Draft a new release**，选好 tag，把 exe/dmg 拖进去即可。

## 六、发布前检查清单

- [ ] 版本号已同步（网页版 3 处 / 桌面版 `desktop/package.json`）
- [ ] `CHANGELOG.md` 已补该版本条目
- [ ] 发布说明已写（网页版 `docs/发布说明_v<版本>.md` / 桌面版 `desktop/docs/release.md`）
- [ ] 本地或 CI 测试全绿（网页版 66 / 桌面版 113）
- [ ] 安装包已在本机实测：安装 → 启动 → 卸载 → 重装
- [ ] 确认 `data/`（含 API Key）未被提交
- [ ] tag 前缀正确（`web-v*` / `desktop-v*`），否则 CI 不会触发对应任务

## 七、常见问题

**Q：推了 tag 但 Actions 没跑？**
① 确认 tag 前缀是 `web-v` 或 `desktop-v`；② 确认工作流文件已在**默认分支**上（Actions 只识别默认分支的工作流定义）。

**Q：`release-desktop` 构建失败在「npm ci」？**
检查 `desktop/package-lock.json` 是否与 `package.json` 同步（本地改依赖后忘提交 lock 文件是常见原因）。

**Q：构建时下载 Electron 很慢/超时？**
CI 在境外环境一般正常；若自建 runner 在国内，参考第五节设置 `ELECTRON_MIRROR`。

**Q：Windows 用户安装时提示「未知发布者」？**
当前未做代码签名，用户点「更多信息 → 仍要运行」即可；后续可购买证书消除（见 [下一步开发计划](下一步开发计划.md)）。
